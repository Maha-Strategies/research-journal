# The Private Atlas Builder

An internal authoring system for evidence-bound research Atlases. It is the private counterpart to the public Research Atlas Gateway: an operator turns source-heavy material into a controlled Atlas through

```
sources → concepts → claims → limitations/status → review → versioned public release
```

It exists so that a future Atlas does not require hand-authoring fifteen route files and a thousand-line data module, and so that the publication gate is enforced by code rather than by attention.

**It does not touch the three hand-authored Atlases.** de Sitter Swampland, Quantum Computing, and Synthetic Intelligence remain TypeScript modules with their own route trees. Their slugs are in `RESERVED_ATLAS_SLUGS` and a builder release that tried to claim one is refused at validation.

---

## Access

Route: **`/operator/atlas-builder`**

Operators are real authenticated users. See
[`atlas-builder-deployment.md`](atlas-builder-deployment.md) for the full
security model, configuration, and the deployment gate.

| Layer | Where | What it does |
|---|---|---|
| Optimistic check | `proxy.ts` | Redirects unauthenticated requests, rotates the Supabase session cookie, sets `X-Robots-Tag: noindex`. **Not a security boundary.** |
| Authorization | `lib/atlas/builder/dal.ts` | `auth.getUser()` revalidates the token with the auth server; role read from the database, never from a JWT claim |
| Action gate | `actions.ts` → `authorized(role)` | Every server action re-checks at the role it requires |
| Row-level security | `supabase/migrations/0004_rls.sql` | Decides what each session can read or write. The only layer that still holds if the others are wrong |

**Roles.** `viewer` reads authorized drafts. `editor` creates and edits their own
drafts and any they are granted write access to. `owner` administers everything
and is the only role that can cut a release. A new account is a `viewer`, which
RLS denies everything to — so requesting a magic link is not itself a way in.

**Fail-closed.** With `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`
unset, every path under `/operator` returns 404 in every environment. The
earlier shared-secret model allowed an unsecured development mode because the
private data was local files; that reasoning did not survive the move to
Postgres, where a misconfigured dev instance could point at a real database.

## Storage: three tiers

The private/public boundary is enforced in three independent ways: private
columns exist only on draft tables, the serializer parses through
`publicAtlasSchema` (Zod strips unknown keys), and a database trigger rejects
any release whose JSON contains a private key at any depth.

| Tier | Location | Committed | Deployed | Served |
|---|---|---|---|---|
| **Private workspace** — drafts, private notes, change log | Postgres, RLS-protected | n/a | n/a | No |
| **Release archive** — immutable, every version ever cut | `atlas_releases` table | n/a | n/a | No |
| **Published corpus** — what public routes read | `content/atlas-releases/published.json` | Yes | Yes | **Yes** |

The public site never queries Postgres. `lib/atlas/builder/releases.ts`
statically imports `published.json`, so publishing is two steps: the Builder
writes an immutable release row, then `npm run atlas:export` regenerates the
file and committing it makes the atlas live. That keeps the public site
independent of database availability and makes going live a reviewable commit.

`published.json` is `[]` today, and every public integration is additive over
it, so the production build is identical to one without the Builder installed.

## Public output contract

A released atlas serves the same shapes as the hand-authored ones, so a client that can read `/atlas/quantum-computing/claims.json` can read a builder atlas without special-casing.

**Pages** — `/atlas/<slug>`, `/claims`, `/claims/<claimId>`, `/concepts`, `/concepts/<conceptId>`, `/sources`, `/sources/<sourceId>`, `/methodology`

**Endpoints** — `metadata.json`, `claims.json`, `concepts.json`, `sources.json`, `context-pack.json`, `context.txt`

**Aggregates** — released atlases join `/atlas/manifest.json`, `/atlas/claims.json`, `/atlas/concepts.json`, `/atlas/sources.json`, the gateway page, and `sitemap.xml` through the *existing* code paths in `lib/atlas/catalog.ts` and `lib/atlas/aggregate.ts`, not a parallel one.

Everything is generated by `lib/atlas/builder/public-output.ts`, which is **deterministic**: same release in, byte-identical bytes out. No `new Date()`, no environment reads. A reader can re-derive the JSON from the archived release record and compare.

### How the route tree stays safe

`app/atlas/[atlasSlug]/` sits beside three *static* siblings. Two independent things keep those safe:

1. `export const dynamicParams = false` — only paths returned by `generateStaticParams` are served; everything else 404s. With no published releases it returns `[]`, so the tree generates zero pages.
2. `RESERVED_ATLAS_SLUGS` refuses the three atlas slugs and the gateway endpoint names at the validation gate.

Removing either would let a builder atlas shadow a hand-authored URL.

## Record model

Schemas in `lib/atlas/builder/schema.ts`; types derived via `z.infer`, matching the convention in `lib/library/schema.ts`.

**The private/public split is structural, not a filter.** Every record type is declared twice: a `public*Schema` with only publishable fields, and a `draft*Schema` extending it with private ones. The serializer parses through the **public** schema, and Zod strips unknown keys — so a private field cannot reach public JSON even if a future edit forgets to exclude it. The alternative, one schema plus a deny-list of private field names, fails *open*: add a field, forget the list, and a note ships. This fails closed.

Two invariants are enforced by the record shape itself, not by a check that runs later:

- a claim's `sourceIds` is non-empty
- a claim's `limitations` is a required non-empty string

A claim without support or without a stated boundary cannot be constructed, so it cannot exist in a state waiting to be caught at review.

Three fields that are routinely collapsed are kept apart, per clause S1:

- **status** — a property of the literature (`established`, `active-research`, `conjecture`, `speculative`)
- **controversy** — how far the field agrees (`uncontested`, `debated`, `contested`)
- **confidence** — the curator's own read (`high`, `moderate`, `low`)

A claim marked `contested` cannot carry status `established`.

### Why `vocabulary.ts` is separate from `schema.ts`

`lib/atlas/catalog.ts` is transitively imported by `components/RegistryList.tsx`, a client component. Anything catalog imports lands in a browser bundle. The vocabularies therefore live in `vocabulary.ts`, which imports nothing; the public-output modules read values from there and import schema *types* with `import type`, which erases. Zod stays on the server.

## Release lifecycle

```
draft ──approve──▶ approved ──release──▶ published ──▶ superseded
  ▲                    │                     │              │
  └───revoke───────────┘                     └──────────────┴──▶ archived
```

`published → draft` does not exist. **A published release is never rewritten.** Correcting one means cutting a new version; the old is marked `superseded` and stays readable. That is clause V2 as code.

Three defences against overwriting a published version:

1. `cutRelease()` refuses a version already present in history, in any state.
2. `FileAtlasStore.archiveRelease()` refuses to overwrite an existing archive file.
3. The archive is written before the served corpus, so a partial failure leaves an unserved archive entry rather than a served release with no record.

Release requires **all** of: `approved` state, a full re-run of the gate at that moment (never a cached result from when the review page rendered), and the operator typing the slug back.

Rollback re-publishes an archived version and clears its `supersededBy`. Nothing is deleted.

## Portable format

`maha-atlas-portable`, version `1.0.0`. Worked example: `docs/atlas-builder-example.json`.

```json
{
  "format": "maha-atlas-portable",
  "formatVersion": "1.0.0",
  "exportedAt": "2026-07-28T00:00:00.000Z",
  "contains": "public-records-only",
  "note": "…",
  "atlas": { "slug": "…", "claims": [], "concepts": [], "sources": [] }
}
```

- **Privacy is declared in the file.** `contains` is `public-records-only` or `includes-private-notes`. A file missing the field is treated as private — a missing declaration on an unknown file is exactly when you want the cautious reading.
- **Export is public by default.** Including private material is an explicit argument, so forgetting the flag produces the safe file.
- **An import is always a draft.** A file claiming `state: "published"` is reset. A file cannot publish itself by being imported.
- A major `formatVersion` mismatch is refused; a minor one warns.

## Commands

```bash
npm test                 # validate:atlas + 64 pure tests
npm run test:rls         # security proof against real Postgres (needs db:start)
npm run test:all         # both
npm run db:start         # local Supabase (needs Docker)
npm run db:reset         # re-apply migrations from scratch
npm run atlas:export     # regenerate published.json from the database
npm run atlas:check-links  # advisory link check
npm run dev
```

Tests use `node --test` with Node's native type stripping — no test framework, no transform, no new dependency. This is why modules under `lib/atlas/builder/` import siblings with an explicit `.ts` extension: Node's resolver requires it, and `allowImportingTsExtensions` in `tsconfig.json` lets tsc and Turbopack read the same files.

## Production status

Persistence, identity, roles, and RLS are implemented. The remaining
limitations, the deployment gate, and the operational runbook are in
[`atlas-builder-deployment.md`](atlas-builder-deployment.md).

Known limitations in brief: draft saves are not atomic, there is no optimistic
concurrency control, role changes are not audited, and the first `owner` must be
promoted by hand against the database.
